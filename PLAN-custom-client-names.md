# Plan: a name for each self-hosted client

Follow-up to [PLAN-custom-redirect-uris.md](PLAN-custom-redirect-uris.md). Goal: the consent screen and the
connection lists name the actual program ("QwenPaw") instead of "Self-hosted client (custom redirect URIs)".

## Current state (PR #1)

- One built-in client, `nextcloud-mcp-custom`, with one shared list of redirect URIs (`oauth_custom_redirect_uris`).
- Its name is the constant `CustomClient::NAME`, shown in the consent heading ("Allow Self-hosted client … to
  access MCP?"), on the "Client:" line, and in both connection lists (`connections.js`).
- Tokens store only `client_id`, not the redirect URI. So with one shared `client_id`, a connection cannot be traced
  back to the program it was made for. The name can't be shown in the connection lists, and access can't be revoked
  for one program alone.

## Approach: one client per program

The admin adds each program separately, with a name and its own redirect URIs. Each gets its own `client_id`,
`nextcloud-mcp-custom-<id>`, where `<id>` is 12 random hex characters generated by the server.

- **Name everywhere:** the `client_id` is stored with every code and token, so the consent screen, the personal
  connection list and the admin connection list can all show the name. No database migration is needed.
- **Redirect URIs bound to a program:** program A can't ask to be sent back to program B's URI.
- **Revocation per program:** deleting a program, or removing one of its URIs, signs out only that program
  (`OAuthStore::deleteForClient` already works per `client_id`).
- **Renaming is safe:** the id is random rather than derived from the name, so a rename doesn't break the
  `client_id` already pasted into the program.
- **The name can be trusted:** it is set by the admin, unlike a CIMD `client_name`, which the client asserts about
  itself. The consent screen can therefore show it as the heading.

PR #1 is not merged, so this replaces the single `nextcloud-mcp-custom` instead of migrating it. Anyone who already
installed the PR branch has to add their programs again and paste the new `client_id` into each one. Each step
below says what changes on the PR #1 branch.

Alternative considered: keep one `client_id` and attach a name to each redirect URI, then pick the name from the
`redirect_uri` of the request. The consent screen could show the name, but the connection lists could not
without a migration adding `redirect_uri` to the token table. Every program would still share one `client_id`,
so revoking one would still revoke all. Rejected.

## Steps

1. **`CustomClient`** (`mcp/lib/OAuth/CustomClient.php`)
   - Store `oauth_custom_clients` as a JSON list of `{id, name, redirectUris}`. This replaces `REDIRECTS_KEY`, and
     `ENABLED_KEY` stays as the switch for the whole feature.
   - `ID_PREFIX = 'nextcloud-mcp-custom-'`. Functions:
     - `clients(IConfig)`: unreadable entries are skipped.
     - `find(IConfig, string $clientId): ?array`.
     - `metadata(array $client): ClientMetadata`: name = the admin's name.
     - `isCustomId(string)`: checks the prefix and 12 hex characters.
   - `validate(mixed $list, array $current)`:
     - at most 20 programs;
     - name trimmed, 1–64 characters, no control characters, and unique ignoring case;
     - 1–20 redirect URIs per program, using the existing URI rules;
     - an entry without an `id` gets a new one from `ISecureRandom`, and an `id` not in `$current` is refused.
2. **Resolution and lock-out**
   - `ClientResolver::resolve`: an id with the prefix resolves only while the feature is on and the program exists.
     Otherwise it fails with `invalid_client` (not redirectable), as today.
   - `ClientResolver::builtInDisabled`: a custom id counts as disabled when the feature is off or the program no
     longer exists. Token exchange, refresh and `AccessTokenAuthenticator` already go through it, so a deleted
     program's tokens stop working even if deleting them failed.
3. **Admin API** (`GrantsController::oauthClients` / `updateOAuthClients`)
   - Return `customClients: [{id, clientId, name, redirectUris}]` instead of `customClientId` and
     `customRedirectUris`.
   - Accept `customClients` as the full list. Compared with the stored list:
     - a program that is gone, or one that lost a redirect URI, has `deleteForClient` run on its `client_id`;
     - a rename, or an added URI, revokes nothing.
   - Turning the feature off revokes every custom `client_id`.
   - Validate everything before writing anything, as today.
4. **Admin page** (`templates/admin.php`, `js/admin-grants.js`, `css/admin.css`), under "Allow self-hosted clients":
   - One card per program with:
     - **Name**;
     - the `client_id` with a Copy button (shown after the first save);
     - **Redirect URIs**, one per line;
     - Save and Delete buttons. Delete asks for confirmation and says the program's connections will be signed out.
   - An "Add program" button. A new program gets its `client_id` when first saved.
   - Hint: "The name is shown to people on the consent screen and in their connections."
5. **Consent screen** (`OAuthController`, `templates/consent.php`)
   - The heading uses the program name: "Allow QwenPaw to access MCP with your account?".
   - The "Client:" line reads "QwenPaw (added by your administrator)". "Returns to:" still shows the host.
6. **Connection lists** (`ConnectionList::client`, `js/connections.js`)
   - Return `kind: 'custom'` with `name`. Show that name, and fall back to "Self-hosted client" if the program was
     deleted between the token check and the list.
   - The name is plain text, set with `textContent`, never HTML.
7. **Translations and docs**
   - New strings in pt_BR and es; strings no longer used are removed.
   - READMEs (en, pt-BR): "add each program with its name; paste its `client_id`".
   - CHANGELOG entry under "Unreleased", amended.
   - The PR #1 description and screenshots are updated.

## Tests

- **Unit tests:**
  - `CustomClientTest`:
    - validation of names: empty, too long, control characters, a duplicate differing only in case;
    - id handling: a forged `id` is refused, and new ids are random and well formed;
    - an unreadable stored value counts as no programs.
  - `TokenFlowTest`:
    - program A's `client_id` with program B's redirect URI is refused;
    - a deleted program's refresh and access tokens are refused.
  - `GrantsControllerTest`:
    - a rename keeps the tokens;
    - removing a URI or a program revokes only that program;
    - turning the feature off revokes all programs.
  - `IssuerRedirectTest` and `AdminAssetsTest`: updated for the new fields and page elements.
- **Real Nextcloud, Playwright, screenshots:**
  - Add "QwenPaw" and a second program, then show the consent heading "Allow QwenPaw…".
  - Show both connection lists naming QwenPaw.
  - Rename QwenPaw: it stays connected.
  - Delete the second program: only it is signed out.
  - Re-run the QwenPaw 2.2.1 end-to-end test with the new `client_id`.

## Open points

- Whether "Allow self-hosted clients" stays as a switch over all programs, or is dropped in favour of one switch
  per program. Plan: keep the one switch. Deleting a program already covers turning a single one off, and a
  per-program switch is easy to add later.
