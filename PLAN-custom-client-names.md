# Plan: a name for each self-hosted client

Follow-up to [PLAN-custom-redirect-uris.md](PLAN-custom-redirect-uris.md). Goal: the consent screen and the
connection lists show the client's real name ("QwenPaw") instead of "Self-hosted client (custom redirect URIs)".

"Client" is the OAuth term (the app that signs in), and the admin section is already called "OAuth clients".
"Provider" would be wrong here: in OAuth, Nextcloud is the provider.

## Current state (PR #1)

- One built-in client, `nextcloud-mcp-custom`, with one shared list of redirect URIs (`oauth_custom_redirect_uris`)
  and one on/off switch (`oauth_custom_client_enabled`).
- Its name is the constant `CustomClient::NAME`, shown in the consent heading ("Allow Self-hosted client … to
  access MCP?"), on the "Client:" line, and in both connection lists (`connections.js`).
- Tokens store only `client_id`, not the redirect URI. So with one shared `client_id`, a connection cannot be traced
  back to the client it was made for. The name can't be shown in the connection lists, and access can't be revoked
  for one client alone.

## Approach: separate self-hosted clients

The admin adds each self-hosted client separately, with a name, its own redirect URIs and its own Enabled setting.
Each gets its own `client_id`, `nextcloud-mcp-custom-<id>`, where `<id>` is 12 random hex characters generated by
the server.

- **Name everywhere:** the `client_id` is stored with every code and token, so the consent screen, the personal
  connection list and the admin connection list can all show the name. No database migration is needed.
- **Redirect URIs bound to a client:** client A can't ask to be sent back to client B's URI.
- **Control per client:** disabling or deleting a client, or removing one of its URIs, signs out only that client
  (`OAuthStore::deleteForClient` already works per `client_id`).
- **Renaming is safe:** the id is random rather than derived from the name, so a rename doesn't break the
  `client_id` already pasted into the client's settings.
- **The name can be trusted:** it is set by the admin, unlike a CIMD `client_name`, which the client asserts about
  itself. The consent screen can therefore show it as the heading.
- **No global switch:** the "Allow self-hosted clients (custom redirect URIs)" switch and
  `oauth_custom_client_enabled` are removed. With no clients added, nothing is accepted, so the feature is still off
  by default.

PR #1 is not merged, so this replaces the single `nextcloud-mcp-custom` instead of migrating it. Anyone who already
installed the PR branch has to add their clients again and paste the new `client_id` into each one. Each step below
says what changes on the PR #1 branch.

Alternative considered: keep one `client_id` and attach a name to each redirect URI, then pick the name from the
`redirect_uri` of the request. The consent screen could show the name, but the connection lists could not
without a migration adding `redirect_uri` to the token table. Every client would still share one `client_id`,
so revoking one would still revoke all. Rejected.

## Steps

1. **`CustomClient`** (`mcp/lib/OAuth/CustomClient.php`)
   - Store `oauth_custom_clients` as a JSON list of `{id, name, enabled, redirectUris}`. This replaces
     `REDIRECTS_KEY` and `ENABLED_KEY`.
   - `ID_PREFIX = 'nextcloud-mcp-custom-'`. Functions:
     - `clients(IConfig)`: unreadable entries are skipped.
     - `find(IConfig, string $clientId): ?array`.
     - `metadata(array $client): ClientMetadata`: name = the admin's name.
     - `isCustomId(string)`: checks the prefix and 12 hex characters.
   - `validate(mixed $list, array $current)`:
     - at most 20 clients;
     - name trimmed, 1–64 characters, no control characters, and unique ignoring case;
     - `enabled` must be a boolean;
     - 1–20 redirect URIs per client, using the existing URI rules;
     - an entry without an `id` gets a new one from `ISecureRandom`, and an `id` not in `$current` is refused.
2. **Resolution and lock-out**
   - `ClientResolver::resolve`: an id with the prefix resolves only while that client exists and is enabled.
     Otherwise it fails with `invalid_client` (not redirectable), as today.
   - `ClientResolver::builtInDisabled`: a custom id counts as disabled when its client is disabled or no longer
     exists. Token exchange, refresh and `AccessTokenAuthenticator` already go through it, so a disabled or deleted
     client's tokens stop working even if deleting them failed.
3. **Admin API** (`GrantsController::oauthClients` / `updateOAuthClients`)
   - Return `customClients: [{id, clientId, name, enabled, redirectUris}]` instead of `customClientEnabled`,
     `customClientId` and `customRedirectUris`.
   - Accept `customClients` as the full list. Compared with the stored list:
     - a client that is gone, was turned off, or lost a redirect URI has `deleteForClient` run on its `client_id`;
     - a rename, an added URI, or turning a client on revokes nothing.
   - Validate everything before writing anything, as today.
4. **Admin page** (`templates/admin.php`, `js/admin-grants.js`, `css/admin.css`)
   - The "Allow self-hosted clients" switch is replaced by a "Self-hosted clients (custom redirect URIs)" heading.
   - One card per client with:
     - **Name**;
     - an **Enabled** checkbox;
     - the `client_id` with a Copy button (shown after the first save);
     - **Redirect URIs**, one per line;
     - Save and Delete buttons. Delete asks for confirmation and says the client's connections will be signed out.
     - Unticking Enabled signs out the client's connections when saved; the hint next to the checkbox says so.
   - An "Add client" button. A new client starts enabled and gets its `client_id` when first saved.
   - Hint: "The name is shown to people on the consent screen and in their connections."
5. **Consent screen** (`OAuthController`, `templates/consent.php`)
   - The heading uses the client's name: "Allow QwenPaw to access MCP with your account?".
   - The "Client:" line reads "QwenPaw (added by your administrator)". "Returns to:" still shows the host.
6. **Connection lists** (`ConnectionList::client`, `js/connections.js`)
   - Return `kind: 'custom'` with `name`. Show that name, and fall back to "Self-hosted client" if the client was
     deleted between the token check and the list.
   - The name is plain text, set with `textContent`, never HTML.
7. **Translations and docs**
   - New strings in pt_BR and es; strings no longer used are removed.
   - READMEs (en, pt-BR): "add each self-hosted client with its name; paste its `client_id`".
   - CHANGELOG entry under "Unreleased", amended.
   - The PR #1 description and screenshots are updated.

## Tests

- **Unit tests:**
  - `CustomClientTest`:
    - validation of names: empty, too long, control characters, a duplicate differing only in case;
    - `enabled` that is not a boolean is refused;
    - id handling: a forged `id` is refused, and new ids are random and well formed;
    - an unreadable stored value counts as no clients.
  - `TokenFlowTest`:
    - client A's `client_id` with client B's redirect URI is refused;
    - a disabled or deleted client's refresh and access tokens are refused.
  - `GrantsControllerTest`:
    - a rename keeps the tokens;
    - removing a URI, disabling a client or deleting it revokes only that client.
  - `IssuerRedirectTest` and `AdminAssetsTest`: updated for the new fields and page elements.
- **Real Nextcloud, Playwright, screenshots:**
  - Add "QwenPaw" and a second client, then show the consent heading "Allow QwenPaw…".
  - Show both connection lists naming QwenPaw.
  - Rename QwenPaw: it stays connected.
  - Disable the second client: only it is signed out and refused; enable it again and it can sign in.
  - Delete the second client: its `client_id` is refused.
  - Re-run the QwenPaw 2.2.1 end-to-end test with the new `client_id`.
